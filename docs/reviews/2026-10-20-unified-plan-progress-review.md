Историческая отрицательная метрика Harbor (ACE 0.567× по токенам) сохранена, неизмеренная стоимость остаётся `unknown`, а не нулём.

3. Ledger отстаёт от `main` на девять слитых PR (раздел 5).

## 3. Новые находки

### F1 (P1, статически выведено) — lease защищает snapshots только в пределах одного хоста и каталога состояния

Lease хранится файлом в `<ACE_STATE_DIR>/qdrant-snapshots/leases/...` и содержит PID. Живость проверяется через `process.kill(pid, 0)`: `ESRCH` означает «мертво», и файл lease удаляется прямо в `activeIndexKeys`. Очистка `pruneQdrantUnleasedSnapshots` затем удаляет все партиции `index_key` рабочей области, которых нет в множестве удерживаемых. Имя коллекции Qdrant зависит от workspace и идентичности модели, но не от каталога состояния или хоста.

Следствия, если один Qdrant используется несколькими процессами:

- процесс на хосте и pod в k3s (для него PR #59 добавил PVC) имеют разные каталоги состояния и не видят lease друг друга;
- общий том между контейнерами с разными PID namespace: чужой PID получает `ESRCH`, lease считается мёртвым и удаляется;
- два пользователя ОС с каталогом по умолчанию `~/.local/state/ace` не видят друг друга.

В каждом случае один процесс может удалить snapshot, который другой ещё читает. Это ровно тот инвариант C-A, который в плане назван главным. Не воспроизведено.

Варианты исправления: хранить lease с TTL и heartbeat там же, где данные (Qdrant или выделенная коллекция); либо включать идентификатор владельца состояния в имя коллекции, чтобы совместное использование стало невозможным; либо запретить очистку без явного single-owner режима. Обязателен реальный тест с двумя процессами и **разными** `ACE_STATE_DIR`.

### F2 (P2, подтверждено в коде) — служебные scroll-запросы тянут полные payload

`listQdrantSnapshotKeys`, `verifyQdrantSnapshotMembership` и `readQdrantSnapshotVectors` вызывают scroll с `with_payload: true`, хотя нужны только `index_key` или `candidate_id`. Payload содержит полный `text` каждого фрагмента. `listQdrantSnapshotKeys` вызывается при каждом старте и перебирает все точки рабочей области. Это работа порядка O(размер всего индекса) на каждый запуск и риск для критерия W04 «1k/10k». Исправление: запрашивать только нужные поля payload. `readQdrantSnapshotVectors` дополнительно держит все векторы прошлого snapshot в памяти.

### F3 (P3, подтверждено в коде) — имя коллекции строится из запрошенной, а не подтверждённой конфигурации

`modelKey` использует `embeddingArtifactDigest` из окружения, по умолчанию `unverified`. Фактический digest из receipt входит только в fingerprint snapshot. При непривязанном режиме два разных артефакта делят одну коллекцию; изоляция держится на `index_key`. Корректность не нарушена, но формулировка DoD C-D про «один verified effective identity в Qdrant namespace» выполнена не полностью.

### F4 (P2, статически выведено) — в процессе нет единого владельца контракта готовности запуска

В `ace-mcp.ts` часть сбоев после первичной подготовки приводит к `throw` и завершению процесса (preflight embedding, LSP), часть — к состоянию `not_ready` с продолжением работы (Qdrant, structural index). Оба поведения безопасны, но для оператора и k3s readiness-проб поведение при сбое зависит от места сбоя. Стоит зафиксировать единую таблицу «сбой → состояние процесса» в runbook. Это замечание по ясности, не по корректности данных.

### F5 (P3, подтверждено в коде) — результат поиска памяти показывает состояние только первого решения

В `searchMemory` для каждого эпизода берётся `decisions.find(...)`, то есть первое решение, ссылающееся на эпизод. Если на эпизод ссылаются несколько решений, остальные теряются. Кроме того, фильтр `as_of` применяется к `occurredAtMs`; время импорта (`importedAtMs`) не учитывается, то есть моделируется только valid time. План требовал явно выбрать семантику; решения об этом в прочитанных документах и коде не найдено.

### F6 (P2, подтверждено) — документы статуса отстают от `main`

Ledger привязан к `33766c721e96…`. После него слиты PR #53, #55, #56, #58, #59, #60, #61, #62, #63. План ссылается на `f935ded2…`. Следствия: ledger не отражает k3s runtime (#59), привязку LSP-snapshot (#56), data-class политику (#63) и resource-budget gate (#62). Читатель не может по ledger определить текущий статус C-B, W11, W12, W15.

## 4. Перекос: проверки доказательств вместо самих доказательств

После baseline слиты, среди прочего: evidence/finalizer-гейты для k3s (#51), backup/restore (#54), supply chain (#46, открыт #64), resource budget (#62), валидация внешних доказательств (#55), code-only и full preflight (#48 и ранее), runner baseline (#58), receipt трассировки (#52). Каждый из них корректен как контракт и честно говорит, что реальный прогон остаётся работой Codex. Но в сумме:

- критический путь плана (W00 → W01–W04 → W05–W08 → W13 → W14) требует **реальных** прогонов: выбор embedding, Serena против TS LS, Graphiti, Vertex, natural-use Harbor;
- в ledger и описаниях PR все эти прогоны значатся как ожидающие; сохранённых результатов после baseline в прочитанных материалах нет (каталог `benchmarks/` не просматривался);
- единственная измеренная оценка пользы ACE остаётся отрицательной (0.567×, forced-use).

Риск: чем больше вычислительных и ревью-усилий уходит на генераторы и валидаторы доказательств, тем позже появится сигнал, оправдан ли сам продукт. План сам разрешает exploratory Harbor запускать сразу, не дожидаясь утверждения моделей.

## 6. Что осталось, по приоритету

1. **F1.** Решить, где живут lease; добавить реальный тест с разными `ACE_STATE_DIR`; до исправления не включать автоочистку snapshots в общих развёртываниях (k3s + host).
2. **Первый реальный сигнал.** Выполнить W00 receipt на exact-main и небольшой natural-use Harbor с тремя рукавами, чтобы проверить гипотезу экономии токенов раньше, чем будет построено остальное.
3. **W01/W02.** Прогнать выбор embedding и Serena на заморожённых данных и получить решения владельца — они блокируют большинство гейтов.
4. **W05/W06.** Реальные Vertex (синтетический corpus) и локальный Graphiti.
5. **F2** (быстрое исправление), затем замеры 1k/10k.
6. **F3, F5**; зафиксировать семантику `as_of` в OpenSpec.
7. **F6.** Обновить ledger до актуального `main` и впредь указывать в заголовке commit и перечень слитых PR после него.
8. **W11 и операции.** Реальный pod → host запуск и восстановление.
9. **Политика очереди PR.** До появления хотя бы одного реального набора доказательств новые PR-генераторы и валидаторы принимать только вместе с прогоном, который их использует.
