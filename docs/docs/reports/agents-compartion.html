Выбор лучшей среды для агента программирования ACE

Срез исследования: 22 октября 2026 г. · Цель: выбрать среду выполнения агента программирования, в которой ACE (Adaptive Context Engine) сможет активно управлять контекстом модели, а не просто предоставлять необязательные MCP-инструменты.

Краткое резюме

Рекомендация: использовать OpenCode V2 как основную среду ACE, Pi как самую быструю и чистую среду для проверки концепции и Hermes Agent как наиболее сильную независимую среду валидации.

Не следует делать Codex или Cursor первой средой ACE. Оба инструмента — отличные базовые варианты, но их документированные и публичные поверхности расширения сейчас не предоставляют принципиально необходимого ACE контроля: возможности заменить полный локальный контекст сообщений непосредственно перед каждым вызовом модели. Теперь это особенно ясно в случае Codex: недавно добавленные хуки PreModelRequest/PostModelRequest явно реализованы только для наблюдения; их результат не интерпретируется как управляющий поток, а входные данные не содержат отправляемых сообщений.

Решающая разница заключается не в вопросе «поддерживает ли агент MCP?», а в вопросе: кто собирает запрос непосредственно перед инференсом? ACE нужна точка локального преобразования запроса, где можно выбрать, удалить, дедуплицировать, суммировать, ранжировать и добавить контекст, сохранив долговечную расшифровку диалога неизменной. MCP по-прежнему полезен для явных операций, таких как ace_expand, получение исходников и диагностика, но сам по себе MCP не даёт ACE контроля над внутренним контекстом запроса модели у агента. В собственной документации Codex MCP описывается как способ предоставить агенту внешние инструменты и информацию, а не как слой переписывания запросов.

OpenCode V2 — лучшая общая цель благодаря тому, что его документированный хук сессии context выполняется непосредственно перед отправкой модели и позволяет изменить собранные system, messages, tools и options для исходящего запроса, не переписывая сохранённую историю диалога. Он также предоставляет хуки до и после выполнения инструментов и переопределяемый путь компактификации, поддерживает субагентов, ориентирован на TypeScript, поддерживает маршруты аутентификации OpenAI/ChatGPT и API провайдеров и имеет очень большую базу пользователей открытого исходного кода.

Pi, возможно, даже лучше подходит для лабораторных экспериментов. Его API расширений предоставляет и context и context_with_system; последний может управлять полной локальной расшифровкой запроса, включая системное сообщение. Pi также предоставляет before_provider_request, изменяемый tool_call, заменяемый результат tool_result, события жизненного цикла сессии и компактификации, постоянные древовидные сессии, добавляемые в конец изменения контекста, SDK и RPC-интерфейс, а также поддержку OAuth Codex. Главный недостаток — Pi намеренно поставляется без встроенных субагентов и режима планирования; их предполагается добавлять расширениями и пакетами.

Hermes Agent лучше всего соответствует самой архитектуре ACE. Его заменяемый ContextEngine содержит документированный метод select_context(..., budget_tokens=...), который выполняется до отправки провайдеру и может вернуть для конкретного запроса другой список сообщений, сохраняя историю. Hermes также назначает постоянным сообщениям и вызовам инструментов стабильные UID, предоставляет наблюдение за жизненным циклом после хода, отслеживает категории токенов кэша и рассуждений и поддерживает параллельных субагентов. Главная цена — граница между языками интеграции: Hermes написан на Python, тогда как ACE сейчас ориентирован на TypeScript, поэтому для эксплуатационного качества лучше использовать небольшой локальный RPC/stdio-адаптер, а не встраивать ACE напрямую.

MiMo Code следует сделать стратегической четвёртой целью и эталонной реализацией, а не первым экспериментом. Он уже реализует большую часть поведения, которое ACE пытается исследовать: постоянную память проекта, автоматические контрольные точки сессии, реконструкцию контекста, бюджетное добавление, прогресс задачи, параллельных субагентов и OAuth Codex/ChatGPT. Его API плагинов также содержит хук experimental.chat.messages.transform. Это делает MiMo очень важным кандидатом, но создаёт и научную проблему: собственная система управления контекстом MiMo может исказить измерение вклада ACE, если её встроенный механизм нельзя чисто отключить или изолировать.

Важно: этот рейтинг — результат архитектурного отбора, а не эмпирический бенчмарк качества агентов. ACE не следует привязывать к одной среде, пока один и тот же контракт преобразования контекста не пройдёт описанные далее эксперименты.

Что ACE действительно требует от среды

Для ACE «интеграция контекста» должна означать больше, чем добавление найденных фрагментов в диалог. Подходящая среда должна позволять ACE выводить следующий запрос к инференсу из долговечного состояния сессии. Среда отвечает за цикл агента, протокол провайдера и выполнение инструментов; ACE становится промежуточным слоем контекста.

Три плоскости интеграции нужно концептуально разделять:

Плоскость интеграции Что она контролирует Полезна для ACE? Типичная технология
Плоскость инструментов и данных Агент выбирает внешнюю операцию и получает её результат. Да — для явного раскрытия, поиска, диагностики и разрешения исходников; недостаточна для обязательного контроля контекста. MCP. Codex и другие агенты предоставляют MCP как внешние инструменты и ресурсы.
Плоскость агента и клиента IDE или оркестратор обращается к агенту как к сервису. Полезна для запуска, возобновления и наблюдения за агентом, но автоматически не раскрывает внутренний запрос агента к инференсу. ACP, app-server/RPC и SDK агентов. Например, Goose может выступать ACP-сервером или использовать Codex/Claude Code как ACP-агентов.
Плоскость преобразования контекста Фактические system/messages/tools/options, отправляемые в следующем запросе к модели. Это обязательная точка контроля ACE. Специфичные для среды хуки плагинов и контекста, например context, у Pi — context_with_system или у Hermes — ContextEngine.select_context.

Важнейшее свойство дизайна — локальное преобразование запроса . ACE не должен разрушительно переписывать долговечную историю чата только для управления тем, что увидит следующая модель. OpenCode явно документирует это различие: его хук контекста запроса изменяет собранный исходящий запрос, оставляя сохранённое состояние диалога нетронутым. Модель сессии Pi также поддерживает преобразования запроса и добавляемые в конец изменения контекста, сохраняя исходные записи сессии, а Hermes описывает выбранный контекст как представление сохранённого состояния для одного запроса к провайдеру.

ACE также должен сохранять инварианты провайдера. Произвольное удаление вызова инструмента при сохранении его результата или удаление специфичных для провайдера элементов рассуждения, на которые ссылается следующий запрос, может сделать запрос недействительным или незаметно снизить качество. Поэтому адаптер должен преобразовывать логические группы, а не произвольные строки: ход пользователя, рассуждение/ответ ассистента, пару вызов инструмента и его результата, резюме контрольной точки и пакет свидетельств. Это одна из причин предпочесть нормализованный хук сообщений на уровне среды перехвату сырых HTTPS-запросов.

Происхождение данных должно оставаться контрактом ACE, а не зависеть от того, какие метаданные случайно сохраняет среда. Минимальная идентичность исходника должна включать зафиксированный снимок рабочей области, путь относительно репозитория, идентификатор blob-объекта, точный диапазон и дайджест содержимого:

type AceEvidenceRef = {
  workspaceId: string;
  snapshot: {
    gitCommit?: string;
    gitTree?: string;
  };
  path: string;
  blobId?: string;
  span: {
    startLine?: number;
    endLine?: number;
    startByte?: number;
    endByte?: number;
  };
  sha256: string;
  retrievalMethod: string;
};

type AceTransformRequest = {
  workspaceId: string;
  sessionId: string;
  requestId: string;
  model: string;
  hardBudgetTokens: number;
  system: unknown;
  messages: unknown[];
  tools: unknown[];
};

type AceTransformResult = {
  system: unknown;
  messages: unknown[];
  tools: unknown[];
  evidence: AceEvidenceRef[];
  retainedIds: string[];
  omittedIds: string[];
  estimatedTokens: number;
  checkpointWatermark?: string;
};

Видимый контекст может содержать компактные непрозрачные ссылки, например ace://workspace/<id>/blob/<sha>#L40-L78, а ACE хранит вспомогательное сопоставление с точным неизменяемым объектом-источником. Это остаётся надёжным даже тогда, когда провайдер удаляет специфичные для среды метаданные из передаваемых данных. Hermes особенно полезен тем, что его постоянные сообщения и вызовы инструментов уже имеют стабильные идентификаторы, которые намеренно не отправляются провайдеру; Pi также сохраняет исходные записи сессии, а изменения контекста влияют только на будущий контекст модели.

Универсальная замена полного запроса не документирована. sessionStart может добавлять контекст; хук после инструмента может добавлять контекст и заменять вывод MCP; жизненный цикл субагента наблюдаем, но preCompact явно предназначен только для наблюдения. Мощные хуки до и после инструмента, с некоторыми ограничениями в облаке. Полноценные изолированные и параллельные субагенты в редакторе, CLI и облаке; SDK предоставляет ту же оболочку. Идентификаторы сессии/диалога, родительские и дочерние ID, а также хуки жизненного цикла рабочей области доступны.
Основные источники: хуки Cursor, субагенты, SDK.
Aider Терминальный парный программист на Python, построенный вокруг Git-осведомлённого цикла чата/редактирования и карты репозитория. Ключи API OpenAI/Anthropic и многих других провайдеров через слой провайдера/LiteLLM; официальная документация различает доступ по API и подписки ChatGPT. В просмотренных официальных материалах не документирован первоклассный жизненный цикл плагина для преобразования запроса. Контекстом внутренне управляют логика coder и карты репозитория. Не через стабильный документированный хук расширения. Для этого, вероятно, потребуется внутренняя интеграция или форк на Python. Внутренние операции редактирования/тестирования/линтинга/Git; это не универсальная система расширений жизненного цикла, сравнимая с Pi/OpenCode. Нет встроенной универсальной системы параллельных субагентов; режим архитектора/редактора — это рабочий процесс с несколькими моделями, а не инфраструктура субагентов. Git-репозиторий — естественная рабочая область; историю чата можно восстановить, но богатый внешний контракт идентичности сессии не является целью продукта.
Основные источники: карта репозитория, аутентификация, сайт проекта.
Claude Code Среда агента программирования Anthropic с поверхностями CLI/IDE/облака/Agent SDK; используются модели Claude, а не GPT. Вход Claude Pro/Max, учётные данные API Anthropic, Bedrock и Vertex AI. Очень богатая экосистема хуков и плагинов: жизненный цикл сессии, промпта, до/после инструмента, субагента и компактификации. В просмотренном API хуков не документирован полный контракт замены сообщений для каждого запроса. Хуки могут добавлять контекст и управлять операциями, но это не эквивалентно владению сборкой запроса. Обширная поддержка хуков инструментов и плагинов. Claude Code и его Agent SDK поддерживают субагентов. Идентификаторы сессий и жизненный цикл расшифровки/сессии доступны хукам и SDK.
Основные источники: хуки Claude Code, аутентификация, ссылки на Agent SDK.
Goose Агент с открытым исходным кодом на Rust, доступный как настольное приложение, CLI и API; MCP и ACP — основные механизмы интеграции. Ключи API провайдеров плюс ориентированные на подписки маршруты через ACP-агентов, таких как Codex и Claude Code. В рассмотренных официальных материалах не обнаружено эквивалентного документированного расширения для локального преобразования сообщений запроса. Потенциально через изменение ядра, но не через документированную поверхность расширений MCP/ACP. Очень сильная экосистема MCP. Поддерживаются независимые параллельные субагенты. Поддержка агента и сессий есть, но стабильный контракт идентичности рабочей области и свидетельств уровня ACE в просмотренных источниках не документирован.
Основной источник: документация Goose.

Выводы по отдельным агентам

OpenCode V2 — самая сильная среда, ориентированная на эксплуатацию. OpenCode V2 лучше всего сочетает владение запросом, зрелость экосистемы и низкую сложность интеграции. Его документированный хук контекста выполняется в цикле агента непосредственно перед отправкой и может изменить системное содержимое, сообщения, инструменты и параметры провайдера только для этого запроса. Хуки инструментов могут изменять аргументы и успешные результаты, а хук компактификации может вернуть собственный результат вместо использования стандартного сумматора среды. Встроенные субагенты уменьшают объём оркестрации, который пришлось бы изобретать ACE. Для ACE это означает, что один адаптер сможет охватить поиск, бюджет токенов, добавление памяти, сжатие результатов инструментов и компактификацию без форка среды.

Главный риск OpenCode — изменчивость API. API плагинов V2 отличается от V1, а существующие плагины V1 не обязательно совместимы автоматически, поэтому ACE должен зафиксировать точную версию OpenCode и поддерживать контрактный тест, проверяющий порядок хуков, локальность сохранения запроса, соответствие вызовов инструментов и поведение компактификации перед обновлением.

Pi — самая сильная экспериментальная оболочка. Pi необычно явно описывает нужные ACE точки интеграции. В документации жизненного цикла отдельно перечислены преобразование контекста запроса, преобразование полной расшифровки, изменение сырого запроса провайдеру, наблюдение за ответом провайдера, изменяемые/блокируемые вызовы инструментов, заменяемые результаты инструментов и жизненный цикл сессии. Долговечная сессия представляет собой дерево записей, а не просто непрозрачный буфер промпта; Pi поддерживает добавляемые в конец записи context_edit , которые влияют на будущий контекст модели, не уничтожая исходную цель или её метаданные. Это исключительно полезно для доказательства того, что ACE может вести полный аудит и одновременно показывать модели уменьшенное представление контекста.

Система компактификации Pi также хорошо поддаётся проверке: её запуск основан на токенах, сохранённая граница представлена явно, исходные записи сессии остаются доступными, а расширения могут настраивать суммирование. Документированные интерфейсы Pi включают TUI, режим событий JSON, RPC-протокол и SDK на TypeScript, что делает автоматизированную интеграцию с бенчмарками относительно простой.

Компромисс — сознательный минимализм. Pi прямо заявляет, что не поставляет субагентов и режим планирования как функции ядра; их предполагается добавлять расширениями и пакетами. Для экспериментов ACE это, вероятно, преимущество, поскольку меньше поведения среды искажает результаты, но для многоагентной эксплуатации OpenCode остаётся более сильной платформой из коробки.

Hermes Agent — лучшее семантическое соответствие. Контракт Context Engine Hermes почти выглядит как спецификация интерфейса ACE: перед вызовом провайдера select_context получает сообщения запроса вместе с бюджетом токенов и может вернуть заменяющий список сообщений; сохранённая история диалога не меняется. Он имеет обратные вызовы жизненного цикла начала/окончания сессии и завершения хода, а также отслеживает расход токенов промпта, завершения, кэша и рассуждений.

Hermes также предоставляет ACE необычно полезную основу для происхождения данных. Сохранённым сообщениям присваиваются стабильные значения message_uid , а вызовам инструментов — стабильные UID вызовов; они переживают ветвление, импорт и экспорт, оставаясь метаданными хранения, а не содержимым, передаваемым модели. ACE по-прежнему будет владеть точным происхождением исходника — коммитом Git, blob, диапазоном и хешем, — но стабильные идентификаторы среды упрощают точное указание, какой видимый модели пакет свидетельств был выведен из какого события сессии.

Главный компромисс — граница реализации. Прямой встроенный плагин Hermes пришлось бы писать на Python, тогда как текущая реализация ACE ориентирована на TypeScript. Для одноразового проверки концепции это приемлемо; для долговечной архитектуры лучше локальный протокол бокового процесса, чтобы ядро ACE не стало зависимым от Python.

MiMo Code — ближайшая существующая система к тезису ACE. MiMo Code особенно важен, потому что уже реализует постоянную память проекта, автоматическую запись контрольных точек, возобновление между сессиями, реконструкцию контекста около лимита модели, бюджетное добавление с ранжированием по важности, состояние прогресса задачи и параллельных субагентов. В текущем README явно документирован OAuth OpenAI через Codex для ChatGPT Pro/Plus, помимо OAuth Xiaomi, провайдеров с ключами API и пользовательских конечные точки, совместимые с OpenAI.

Его внутренние определения плагинов идут дальше: API предоставляет sessionID, идентичность рабочей области, хуки до и после инструмента, хуки параметров чата и точку расширения experimental.chat.messages.transform. Типы траекторий также содержат ID сообщений/частей, сведения о токенах и стоимости и поля, связанные с происхождением и исходниками.

Это делает MiMo отличной эталонной реализацией и целью для абляционных экспериментов, но менее чистой первой средой ACE. Если собственные запись контрольных точек, реконструкция контекста и добавление памяти MiMo останутся активными, результат «ACE включён» перестанет чисто измерять ACE. До включения MiMo в первую тройку эксперимент должен проверить, можно ли независимо отключить встроенную память и реконструкцию, сохранив тот же цикл агента и маршрут провайдера.

Codex — лучшая база сравнения, но сейчас с неподходящей поверхностью контроля. Codex теперь имеет широкую систему хуков вокруг начала/окончания сессии, отправки пользовательского промпта, использования инструментов, компактификации и субагентов, а App Server предоставляет программный контроль потоков/сессий и операции компактификации. Аутентификация является официальной и простой: Codex поддерживает вход через ChatGPT и маршруты с ключом API OpenAI на применимых поверхностях.

Однако решающий результат проверки текущего исходного кода Codex однозначен. PreModelRequest и PostModelRequest уже существуют, но файл исходного кода начинается с объявления, что это «хуки жизненного цикла только для наблюдения». Событие до модели содержит идентичность сессии/хода/cwd/расшифровки/модели, но не изменяемую расшифровку запроса, а результат обработчика намеренно записывается в журнал, а не интерпретируется. Поэтому одно лишь наличие хука с именем PreModelRequest не решает задачу интеграции ACE.

Это существенно меняет рекомендацию: Codex должен остаться самой важной нативной базой сравнения, но архитектуру ACE не следует строить вокруг хуков Codex, пока OpenAI не предоставит стабильный контракт изменения, например TransformModelRequest или эквивалент. Форк Codex, конечно, мог бы добавить такой хук, но это создаст постоянную нагрузку по слиянию изменений с быстро меняющимся официальным агентом.

Cursor — доказательство важности инженерии контекста на уровне среды, но не открытая точка интеграции ACE. Cursor прямо описывает собственную специализированную для модели среду: промпты и формы инструментов различаются в зависимости от выбранной модели, а среда Cursor управляет сборкой каждого запроса к инференсу. В сентябре 2026 года Cursor сообщил, что изменения в сборке запроса, повторном использовании контекста и распределении работы снизили стоимость токенов на 7% без ухудшения качества в производственных измерениях.

Публичные хуки Cursor мощны для безопасности и наблюдаемости, но не предоставляют такого же внутреннего контроля сборки запроса. sessionStart может добавлять исходный контекст; хуки после инструмента могут добавлять дополнительный контекст и для MCP-инструментов заменять видимый модели вывод; жизненный цикл субагента наблюдаем, но preCompact явно предназначен только для наблюдения, и универсальный хук «заменить текущую расшифровку модели» не документирован. SDK Cursor в публичной бете запускает агентов с той же оболочкой Cursor, а не передаёт прикладному коду сырой запрос к модели.

Поэтому Cursor следует считать важной конкурентной контрольной средой, а не первой средой для независимо управляемого движка ACE.

Aider — ценная простая база сравнения. Главная контекстная возможность Aider — карта репозитория. Она строит представление символов и зависимостей репозитория, ранжирует релевантные части и помещает это представление в настраиваемый бюджет токенов перед отправкой вместе с запросами на изменения. Это даёт ACE полезную базу сравнения с относительно простой и хорошо понятной формой инженерии контекста кода.

Aider менее привлекателен как среда ACE, потому что просмотренная официальная документация не предоставляет стабильного хука плагина, заменяющего каждый исходящий список сообщений. Доступ к GPT обычно идёт через OpenAI/API провайдеров, а не через вход по подписке ChatGPT. Глубокая интеграция возможна благодаря открытому исходному коду проекта, но это была бы внутренняя интеграция на Python, а не узкий переносимый адаптер, который предпочтителен для ACE.

Claude Code — отличная архитектура расширений, но неподходящее семейство моделей для требования GPT. Claude Code имеет развитую экосистему хуков, плагинов и Agent SDK, встроенных субагентов и поддерживает вход Claude Pro/Max, а также маршруты Anthropic API, Bedrock и Vertex. Просмотренный публичный API хуков не документирует произвольную замену полного списка сообщений перед инференсом так, как это делают Pi, OpenCode или Hermes. Поэтому Claude Code полезен как архитектурная база сравнения, но не как основная цель ACE+GPT.

Goose — отличная история с открытыми стандартами, но более слабая точка интеграции ACE. Goose имеет открытый исходный код, лицензию Apache-2.0, доступен как настольное приложение, CLI и API, поддерживает субагентов, крупную экосистему MCP и интеграцию ACP с такими агентами, как Codex. Архитектурная проблема в том, что при использовании Codex через ACP внутренним циклом инференса всё равно владеет Codex. Поэтому вложение Codex внутрь Goose не даёт ACE магического доступа к внутреннему запросу модели Codex. В просмотренных официальных материалах Goose не обнаружено плагина замены контекста запроса в стиле Pi/OpenCode/Hermes; до выбора Goose в качестве среды ACE потребуется дополнительная проверка на уровне исходного кода.

Рекомендуемая архитектура интеграции ACE

Наиболее сильный долгосрочный дизайн — не «ACE для OpenCode» и не «ACE для Pi». Это независимое от агента ядро ACE плюс тонкие адаптеры сред.

flowchart TD
    U[Задача пользователя] --> H[Цикл агента среды]
    H --> A{Адаптер среды ACE}
    A --> W[Разрешить идентичность рабочей области + сессии]
    W --> C[Движок контекста ACE]
    C --> R[Поиск / ранжирование]
    C --> M[Память / контрольные точки]
    C --> B[Бюджет токенов + дедупликация]
    C --> P[Происхождение / точные ссылки на исходники]
    R --> T[Преобразованный запрос]
    M --> T
    B --> T
    P --> T
    T --> H
    H --> L[GPT / провайдер]
    L --> H
    H --> E[События инструментов]
    E --> A
    A --> C

    C -. только явное раскрытие .-> MCP[Необязательные MCP-инструменты ACE]
    MCP -. ace_expand / диагностика .-> H

Адаптер среды должен выполнять только пять задач: нормализовать сообщения среды в представление ACE, вывести стабильную идентичность рабочей области/сессии/запроса, вызвать преобразователь ACE, проверить безопасность возвращённого графа сообщений для провайдера и перевести его обратно в тип запроса среды. Поиск, ранжирование, политика памяти, идентичность исходников и решения по бюджету относятся к ядру ACE.

Для переносимости производственной границей, вероятно, должен стать локальный протокол бокового процесса , даже если первые адаптеры на TypeScript смогут вызывать ACE внутри процесса. Небольшой протокол stdio или Unix-сокета позволит OpenCode и Pi использовать тот же процесс ACE, что и Hermes, а позднее упростит поддержку Rust-сред, таких как Goose, без переписывания ACE. Это архитектурная рекомендация, а не требование, наложенное какой-либо из рассмотренных сред.

MCP должен остаться, но перейти из плоскости контроля в плоскость явных возможностей. Например:

Автоматический путь:
хук контекста среды
    → ace.transform(request)
    → преобразованный запрос обязателен для каждого инференса

Путь, выбранный моделью по необходимости:
ace_expand(evidence_handle)
ace_source(evidence_handle)
ace_memory_search(query)
ace_checkpoint_status()
ace_explain_context(request_id)

Это решает исходную архитектурную проблему: модели больше не нужно «решать использовать ACE», чтобы ACE мог экономить токены контекста. Среда автоматически вызывает ACE на границе запроса. Модель по-прежнему может намеренно попросить ACE раскрыть свидетельство, когда ей нужна точная детализация.

Адаптер также должен записывать запись решения по контексту для каждого запроса к инференсу. Как минимум в ней должны быть ID запроса, хоста/сессии/рабочей области, исходная оценка токенов, оценка после преобразования, ID сохранённых/удалённых сообщений, дескрипторы свидетельств, дайджесты исходников, бюджет, водяной знак контрольной точки, задержка преобразования и состояние ошибки/резервного режима. Это даст бенчмаркам достаточно свидетельств, чтобы определить, действительно ли ACE участвовал, а не просто был установлен.

Режимы fail-open и fail-closed должны настраиваться для каждого типа запуска. В интерактивной работе обычно следует использовать fail-open: если ACE упал, сохранить неизменённый запрос среды, чтобы разработчик мог продолжить. В бенчмарках и релизных проверках следует использовать fail-closed, когда эксперимент требует гарантий происхождения, идентичности исходников или бюджета контекста; иначе незаметно пропущенный запрос ACE загрязнит результаты.

Кэширование провайдера требует отдельного рассмотрения. Переписывание контекста может уменьшить номинальное число входных токенов, разрушив повторно используемый префикс промпта и увеличив расход некэшированных токенов. Собственный анализ Cursor подчёркивает, что его среда контролирует и сборку запроса, и повторное использование контекста, а производственная оценка стоимости учитывала как кэшированный, так и некэшированный ввод. Поэтому бенчмаркам ACE нужны категории токенов чтения и записи кэша, а не только «токены промпта».

Проверочные эксперименты и бенчмарки

Первый эксперимент должен не проверять качество поиска. Он должен доказать, что ACE действительно владеет границей запроса. Иначе большой бенчмарк может показать впечатляющие цифры, проверяя не адаптивный контроль контекста, а необязательное использование инструментов.

проверки концепции плоскости контроля. Реализуйте минимально возможный адаптер для OpenCode V2 и Pi. Сначала ACE выполняет детерминированное преобразование: сохраняет системные инструкции, последний ход пользователя и корректные группы вызова инструмента с результатом, удаляет один известный избыточный ранний блок, а затем добавляет синтетическую запись свидетельства с проверяемым маркером. Запустите задачу, заставляющую модель сделать несколько вызовов. Запуск считается успешным только если каждый применимый запрос создаёт запись решения по контексту, провайдер получает преобразованное представление, а долговечная расшифровка среды остаётся неизменной.

Для Pi дополнительно проверьте семантику context и context_with_system, а также замену результата инструмента. Для OpenCode проверьте, что изменения контекста локальны для запроса и что переопределение компактификации остаётся совместимым. Соответствующие API среды прямо заявляют такое поведение, поэтому эти проверки должны стать исполняемыми тестами совместимости, привязанными к версиям среды.

Проверка соблюдения бюджета. Создайте диалог с намеренно чрезмерно большими прежними результатами инструментов и задайте бюджеты ACE, например 16K, 32K и 64K видимых модели токенов. Для каждого запроса измеряйте оценку токенов до преобразования, оценку после преобразования, фактические входные токены провайдера, токены чтения/записи кэша, превышение бюджета и задержку преобразования. Среда проходит проверку только если ACE может обеспечить верхнюю границу, не нарушив структуру сообщений инструментов.

Проверка происхождения данных. Зафиксируйте каждый репозиторий на точном коммите Git. Каждый элемент свидетельства ACE должен разрешаться в путь/диапазон, дайджест содержимого которого совпадает с зафиксированным blob. После создания свидетельств измените рабочее дерево и подтвердите, что ACE либо разрешает исходный неизменяемый объект, либо помечает ссылку как устаревшую, а не молча указывает на другой текст. Бенчмарк не должен выводить или восстанавливать ревизии исходников из эталонных ответов.

Проверка контрольных точек и возобновления. Запустите долгую задачу программирования, прервите её в детерминированных точках — после исследования, после неудачного теста, после частичного редактирования и сразу после компактификации, — затем перезапустите процесс. Измерьте, какая доля уже выполненного исследования повторяется, время и токены до первого полезного действия после возобновления, перечитанные исходные файлы, повторно запущенные тесты, итоговое качество и то, разрешается ли по-прежнему свидетельство из контрольной точки. Встроенная архитектура контрольных точек MiMo полезна как группа сравнения, поскольку явно поддерживает структурированные контрольные точки сессии и восстанавливает контекст из состояния контрольной точки, памяти и прогресса задачи.

Проверка переносимости между средами. Прогоните одинаковую детерминированную политику ACE через OpenCode, Pi и Hermes. ACE должен выдавать эквивалентные ID сохранённых свидетельств и решения по бюджету для эквивалентных логических расшифровок, даже если схемы сообщений сред различаются. Именно этот эксперимент доказывает, что ACE — движок, а не функция, случайно приваренная к одному агенту.

Бенчмарк качества агента. После прохождения плоскости контроля используйте для каждой задачи четыре группы:

Группа Конфигурация На какой вопрос отвечает
A Нативная среда Что делает агент программирования без ACE?
B Среда + пассивные MCP-инструменты ACE Использует ли модель ACE добровольно, если он просто доступен?
C Среда + обязательное преобразование контекста ACE Улучшает ли активное внешнее управление контекстом границу качества и стоимости?
D Среда + активный ACE + контрольная точка/возобновление Улучшает ли постоянное состояние контекста работу после прерываний и на длинном горизонте?

Это разделение критически важно. Группа B измеряет принятие инструментов. Группа C измеряет сам тезис ACE. Если объединить их, невозможно будет различить «полезен инструмент поиска» и «полезен внешний контроллер контекста».

Для корпуса задач используйте смесь, а не одну таблицу лидеров:

  • Замороженные реальные задачи исправления ошибок с исполняемыми тестами и неизменяемыми ревизиями исходников. Это самые важные задачи, потому что качество результата проверяется механически.
  • Задачи репозиториев в стиле SWE с явно зафиксированными ревизией исходников и средой тестирования. Не оценивайте задачи, для которых состояние исходников нельзя воспроизвести точно.
  • Задачи понимания репозитория и поиска только при наличии официального снимка исходников. Если набор данных в стиле RepoBench предоставляет эталонные свидетельства без воспроизводимой ревизии исходников, помечайте этот набор задач как ЗАБЛОКИРОВАНО , а не восстанавливайте коммиты по эталонным фрагментам.
  • Задачи с прерываниями на длинном горизонте , специально созданные для проверки контрольных точек и возобновления, а не только генерации одноразового патча.

С учётом уже ведущейся работы ACE вокруг Harbor, Harbor может остаться внешним воспроизводимым исполнителем задач, а каждый адаптер среды следует считать заменяемым бэкендом выполнения. Манифест зафиксированных исходников нужно повторно проверять до и после запуска, а результаты испытаний связывать по явному идентификатору испытания, а не по порядку каталогов.

Основные метрики должны быть такими:

Семейство метрик Измерения Почему это важно
Качество Принятая/пройденная задача, пройденные тесты, регрессии, подтверждённая корректность патча Экономия токенов бессмысленна, если ACE ухудшает агента.
Стоимость модели Некэшированный ввод, кэшированный ввод при чтении, ввод при записи в кэш, вывод, токены рассуждений и стоимость провайдера Переписывание контекста может изменить экономику кэша промпта.
Накладные расходы ACE Вызовы поиска, работа эмбеддингов, токены вспомогательных моделей, процессорное время, задержка индекса и запроса Собственная стоимость ACE должна входить в общую стоимость решения задачи.
Эффективность контекста Переданные байты/токены, доля дублирования контекста, покрытие уникальных исходников, доля повторяющихся результатов инструментов Показывает, как именно были получены изменения числа токенов.
Поведение агента Вызовы инструментов, чтения файлов, повторные чтения файлов, тесты, повторы, вызовы субагентов, число запросов к модели ACE может перенести работу из контекста модели в дополнительные раунды взаимодействия.
Целостность плоскости контроля Доля подходящих запросов, подвергшихся преобразованию, нарушения бюджета, некорректные преобразования, события fail-open Доказывает, что «ACE включён» действительно означает участие ACE.
Происхождение данных Разрешаемые дескрипторы исходников, несовпадения дайджестов, устаревшие ссылки, проверка точных диапазонов Не позволяет контексту превратиться в неотслеживаемый сгенерированный текст.
Возобновление Повторная работа после перезапуска, токены на восстановление, время до первого полезного действия, изменение итогового успеха Проверяет, сохраняет ли контрольная точка действительно полезное состояние.
Задержка Полное время, время до первого токена, задержка преобразования, задержка поиска Сокращение токенов на 20%, удваивающее задержку, может быть неприемлемым в интерактивной работе.

Главной метрикой эффективности должно быть общее число токенов на принятую задачу с учётом качества, а не сырое сокращение токенов. Если нативная версия успешна, а ACE — нет, не следует рекламировать неудачный запуск ACE как экономию только потому, что он рано остановился. В парных сравнениях сообщайте экономию токенов/стоимости только для успешных пар сопоставимого качества, а затем отдельно сообщайте изменение доли успеха. Так бенчмарк остаётся на границе Парето по качеству, стоимости и задержке, а не оптимизирует одно число.

Каждый запуск бенчмарка должен сохранять: версию/коммит среды, версию адаптера, коммит ACE, маршрут модели/провайдера, тип маршрута аутентификации, SHA зафиксированного репозитория, дайджест контейнера/образа при наличии, конфигурацию инструментов, точную политику ACE, случайное зерно там, где оно имеет смысл, полный расход токенов, записи решений по контексту и хеши созданных артефактов. Это позволит последующему результату доказать не только полученный балл, но и какая система фактически его получила.

Приоритетная рекомендация, риски и нерешённые проверки

OpenCode V2 — рекомендуемая основная среда. Он даёт лучший баланс свойства, которое ACE безусловно требует — локального преобразования сообщений запроса, — и практических инженерных факторов: TypeScript, API плагинов, встроенные субагенты, гибкость провайдеров, несколько поверхностей развёртывания и очень сильное сообщество. Адаптер может оставаться небольшим, потому что OpenCode уже владеет сложными частями цикла агента программирования. Главный риск — развитие API V2, поэтому ACE должен зафиксировать среду и постоянно выполнять набор проверок соответствия адаптера перед обновлениями.

Pi — рекомендуемый первый проверки концепции, если цель — доказать ACE максимально быстро и чисто. Его API расширений предоставляет почти все нужные точки: преобразование только диалога, преобразование полной расшифровки, преобразование полезной нагрузки провайдера, преобразование входа/вывода инструмента, компактификацию, сессии, SDK и RPC. Поскольку Pi намеренно минималистичен, успешный эксперимент с меньшей вероятностью объясняется скрытым встроенным поиском или памятью. Компромисс в том, что некоторые производственные удобства — особенно встроенная оркестрация субагентов — не являются функциями ядра.

Hermes — рекомендуемая третья среда. Это лучшее независимое доказательство того, что абстракция ACE переносится за пределы экосистемы в стиле TypeScript/OpenCode. Его Context Engine уже имеет правильную семантическую границу и явно получает бюджет токенов; стабильные идентификаторы сообщений делают работу с происхождением и аудитом необычно чистой. Дополнительная стоимость интеграции приемлема, потому что это должна быть вторая реализация стабильного протокола адаптера ACE, а не одноразовый порт.

MiMo Code должен идти после этих трёх. В конечном счёте это может быть одной из самых сильных практических сред, поскольку сочетает GPT через OAuth Codex, родословную TypeScript/OpenCode, явные хуки преобразования сообщений, богатое происхождение траекторий, субагентов и сложное постоянное управление контекстом. Но первые научные свидетельства ACE не должны исходить от среды, чьи собственные встроенные возможности настолько сильно пересекаются с ACE. Сначала нужно определить, можно ли независимо отключить память, контрольные точки и реконструкцию контекста MiMo, а также стабильно ли ведёт себя experimental.chat.messages.transform при повторах, работе субагентов и компактификации.

Codex должен остаться основной базой сравнения, а не быть отброшен. Он особенно важен, поскольку ACE в конечном счёте хочет превзойти или дополнить его нативное поведение для программирования с GPT. Но сегодняшние свидетельства на уровне исходников говорят, что новые хуки запросов модели являются наблюдателями, а не изменяющими механизмами. Чистым путём вперёд был бы стабильный хук основного проекта преобразования запроса; пока его нет, интеграция ACE через форк Codex будет дороже и менее переносимой, чем сначала доказательство концепции в OpenCode/Pi/Hermes.

Cursor следует считать высококачественной эталонной средой. Cursor сам является сильным доказательством важности инженерии контекста: компания публично описывает владение сборкой запроса, специфичными для модели промптами и инструментами, повторным использованием контекста и распределением работы субагентов. Его публичная поверхность расширений просто не передаёт такое же владение внешнему плагину ACE.

Оговорка об аутентификации. «Проект стороннего агента поддерживает OAuth Codex/ChatGPT» — не то же самое, что «OpenAI гарантирует этот путь аутентификации навсегда для каждого стороннего продукта». Поэтому Pi, OpenCode, Hermes и MiMo следует проверять с тем же актуальным маршрутом аутентификации, который вы собираетесь использовать, а в бенчмарках ACE фиксировать, применялся ли в каждом запуске бэкенд подписки/Codex или прямой API провайдера. Для научного сравнения разных сред самым чистым контролем при приемлемой стоимости будет прямой API провайдера с одинаковой моделью и настройками; запуски по подписке/OAuth затем проверят реальный эксплуатационный путь.

Оставшиеся неоднозначные или зависящие от версии пункты, которые нужно проверить до реализации:

Агент Статус Проверка
OpenCode V2 В основном определено Зафиксировать точный выпуск V2 и проверить порядок хука контекста относительно компактификации, повторов, вызовов субагентов и сериализации провайдера.
Pi В основном определено Проверить стабильность текущего OAuth openai-codex и убедиться, что context_with_system сохраняет все специфичные для провайдера инварианты рассуждений и инструментов для выбранной GPT-модели. OAuth Codex начинался в Pi как экспериментальный провайдер.
Hermes Контракт контекста определён; эксплуатационные детали требуют проверки Проверить точный путь провайдера Codex OAuth в зафиксированном выпуске и определить каноническое сопоставление сессий/рабочих областей Hermes с ID ACE.
MiMo Code Преобразование сообщений явно экспериментальное Определить, можно ли независимо отключить встроенные контрольные точки, память и реконструкцию контекста; установить порядок преобразований и семантику ошибок.
Codex Текущий ответ ясен Отслеживать основной проект на предмет будущего изменяемого хука запроса модели. Текущая реализация явно предназначена только для наблюдения.
Cursor Публичная поверхность недостаточна Проверить у Cursor, предоставляет ли поверхность SDK/enterprise-плагинов непубличный или недавно выпущенный API промежуточного слоя сборки запроса; в текущем справочнике хуков он не документирован.
Aider Не определено В просмотренной официальной документации не найден первоклассный API плагина для преобразования контекста; проверять внутренние части Coder и провайдера имеет смысл только если Aider станет серьёзной целью.
Claude Code Частично Повторно проверить будущие выпуски хуков на наличие полного события преобразования запроса модели; богатство текущих хуков и плагинов само по себе не доказывает владение полным запросом.
Goose Не определено для преобразований уровня ACE Изучить путь сборки запроса провайдера на Rust, если интеграция с открытыми стандартами станет приоритетом; одной поддержки MCP/ACP недостаточно, чтобы установить наличие изменяемой внутренней точки запроса.

Итоговое решение: собрать один нормализованный API преобразования контекста ACE, сначала реализовать адаптеры Pi и OpenCode V2, потребовав от них прохождения одинаковых проверок плоскости контроля, происхождения и бюджета. После стабилизации контракта добавить Hermes как третью независимую реализацию. Сохранить нативный Codex как основную GPT-базу сравнения, добавить MiMo Code как эталонную группу памяти и контрольных точек и использовать Cursor как коммерческую контрольную среду. Такая последовательность проверяет тезис ACE, не заставляя сначала внедрять ACE в агента, чья публичная API-поверхность фактически не даёт ему контроля над контекстом модели.
